# ThingLens 개발 계획서

> ThingsBoard에 저장된 **디바이스(Device)와 에셋(Asset)의 정보 상관관계**를 수집·분석·시각화하는 앱

- 문서 버전: v0.6 (Cassandra 저장소 · 앱 별도 서버 · 무기한 보존 반영)
- 작성일: 2026-11-15
- 상태: 검토 대기 (§0 확정 사항 반영, §10 남은 확인 사항 회신 후 확정)

## 1. 목표와 범위

### 1.1 해결하려는 문제

ThingsBoard는 디바이스·에셋·관계(Relation)·속성(Attribute)·텔레메트리(Timeseries)·알람을 저장하지만,
기본 UI만으로는 다음 질문에 답하기 어렵습니다.

| 질문 | 예시 |
|---|---|
| 구조는 올바른가? | 어느 에셋에도 속하지 않은 고아 디바이스는? 부모가 둘 이상인 디바이스는? 순환 관계는? |
| 메타데이터는 일관적인가? | 에셋의 `location`과 하위 디바이스의 `location`이 다른 경우는? 프로파일별 필수 속성이 빠진 엔티티는? |
| 데이터는 어떻게 함께 움직이는가? | 같은 건물(에셋) 안 온도 센서끼리의 상관계수는? 펌프 전류와 배관 압력 사이 시간 지연(lag)은? |
| 이상은 함께 발생하는가? | 특정 에셋 하위 디바이스들의 알람이 같은 시간대에 동시에 발생하는가? |
| 빠진 관계는 없는가? | 데이터 패턴상 같은 에셋에 속해야 할 것 같은데 관계가 없는 디바이스는? |

### 1.2 "상관관계"의 정의 (3계층) + 데이터 의미 이해

본 앱은 상관관계를 세 계층으로 나누어 다루며, 그 기반으로 **데이터 의미 추론 계층**을 둡니다.

0. **데이터 의미 추론 (Semantics)** — 텔레메트리·속성 키의 데이터 종류(타입)와 의미(온도, 전력, 위치 등)를 자동 추론 → 상관 분석에서 "비교 가능한 키"를 자동으로 묶는 기반
1. **구조적 상관관계 (Topology)** — ThingsBoard `EntityRelation` 기반 그래프
2. **메타데이터 상관관계 (Attribute)** — 속성 값의 일치·유사도·누락
3. **행위적 상관관계 (Behavior)** — 텔레메트리 시계열 통계 상관 및 알람 공발생

### 1.3 핵심 설계 원칙: ThingsBoard 무부하(Low-impact)

- ThingsBoard는 운영 시스템이므로, 본 앱은 **백그라운드 스케줄러가 정해진 요청 예산 안에서 천천히** 데이터를 수집합니다.
- 분석은 항상 **로컬 캐시**를 대상으로 실행하며, 사용자의 분석 요청이 ThingsBoard로 직접 요청을 폭증시키지 않습니다.
- TB 응답 지연·오류가 늘어나면 스스로 속도를 늦추고(적응형 스로틀링), 필요하면 수집을 일시 정지합니다.

### 1.4 범위

| 포함 (In scope) | 제외 (Out of scope, 초기 버전) |
|---|---|
| ThingsBoard REST API를 통한 **읽기 전용** 데이터 수집 | ThingsBoard 데이터 쓰기/수정 (관계 자동 생성 등) — 추천만 제공 |
| **저부하 백그라운드 스케줄링 수집** (요청 예산·시간대·적응형 스로틀링) | |
| 텔레메트리·속성의 **데이터 타입 및 의미 추론** | |
| 관계 그래프 분석·시각화 | 실시간 스트리밍 분석 (WebSocket) — v1.0 이후(Phase 9) 검토 |
| 속성 정합성 검사 | 머신러닝 기반 예측 모델 |
| 텔레메트리 상관 분석 (피어슨/스피어먼/지연 상관) | ThingsBoard 위젯/Rule Engine 플러그인 형태 배포 |
| 알람 공발생 분석, 누락 관계 추천 | 다중 테넌트 SaaS 운영 |
| 분석 결과 리포트(CSV/HTML) 내보내기 | |
| 데이터 품질 점검, 상관 변화 감지, 원인·영향 추적, 중복·공백 분석 (§13) | |
| 엔티티 360° 뷰, 변경 이력, 정기 리포트·알림, 자연어 질의 (§13) | |
| 고객 범위 접근 제어, 조치용 내보내기(TB 가져오기 형식), 표준 명명 제안, 데이터셋 내보내기 (§13) | |

## 2. 사용자와 주요 시나리오

| 사용자 | 시나리오 |
|---|---|
| IoT 플랫폼 운영자 | 전체 테넌트의 관계 구조 건전성 점검, 고아/중복 엔티티 정리 |
| 설비/현장 엔지니어 | 특정 에셋(공장·라인·건물) 하위 센서 간 상관 히트맵으로 이상 센서 식별 |
| 데이터 분석가 | 에셋 단위로 정렬된 시계열 데이터셋을 추출하여 추가 분석 |

대표 사용자 흐름:

1. ThingsBoard 연결 정보 등록 → 연결 테스트 → 요청 예산(속도·시간대) 설정
2. 백그라운드 스케줄러가 메타데이터·키 카탈로그·샘플을 천천히 수집 (진행률 확인 가능)
2-1. **데이터 카탈로그**에서 자동 추론된 키 타입·의미 검토, 낮은 신뢰도 항목 확정
3. **토폴로지 뷰**에서 에셋 트리/그래프 탐색, 이슈 목록 확인
4. 에셋 하나를 선택 → 하위 디바이스의 텔레메트리 키·기간·집계 간격 선택 → **상관 분석 실행**
5. 히트맵·산점도·지연 상관 그래프 확인 → 결과 리포트 내보내기

## 3. ThingsBoard 연동 설계

### 3.1 사용할 API (PE 기준, 3.x·4.x 공통)

| 용도 | 엔드포인트 | 비고 |
|---|---|---|
| 인증 | `POST /api/auth/login`, `POST /api/auth/token` | JWT + Refresh 토큰. `X-Authorization: Bearer <token>` |
| 디바이스 목록 | `GET /api/tenant/deviceInfos?pageSize&page` | 페이지네이션 (`hasNext`) |
| 에셋 목록 | `GET /api/tenant/assetInfos?pageSize&page` | |
| 프로파일 | `GET /api/deviceProfileInfos`, `GET /api/assetProfileInfos` | |
| **대량 조회(권장)** | `POST /api/entitiesQuery/find` | Entity Data Query: 필터(`entityType`, `deviceType`, `assetType`, `relationsQuery` 등) + 최신값 + 키 필터를 한 번에 조회 |
| 관계 | `GET /api/relations/info?fromId&fromType`, `POST /api/relations` (EntityRelationsQuery) | `direction`, `maxLevel`, `relationType` 필터 |
| 속성 키/값 | `GET /api/plugins/telemetry/{type}/{id}/keys/attributes`, `.../values/attributes/{scope}` | `SERVER_SCOPE` / `SHARED_SCOPE` / `CLIENT_SCOPE` |
| 텔레메트리 키 | `GET /api/plugins/telemetry/{type}/{id}/keys/timeseries` | |
| 텔레메트리 값 | `GET /api/plugins/telemetry/{type}/{id}/values/timeseries?keys&startTs&endTs&interval&agg&limit` | `agg=AVG/MIN/MAX/SUM/COUNT/NONE`. Cassandra 환경에서 짧은 간격 집계는 내부적으로 구간 수만큼 조회가 쪼개짐 → 미세 간격은 원시값 수집 후 로컬 집계 (§3.6) |
| 알람 | `GET /api/v2/alarm/{type}/{id}` 또는 `/api/alarm/{type}/{id}` | 버전에 따라 경로 상이 → 어댑터로 흡수 |
| **[PE] 엔티티 그룹** | `GET /api/entityGroups/{groupType}`, `GET /api/entityGroup/{id}/entities` | 디바이스·에셋 그룹 소속 → 관계와 별개의 구조 정보 |
| **[PE] 소유자 계층** | `GET /api/customers`(하위 고객 포함), 엔티티 `ownerId` | 고객/하위 고객 계층별 엔티티 분포 |

**PE 접근 계정**: Tenant Administrator 대신 PE의 **Generic Role**로 `READ`, `READ_ATTRIBUTES`, `READ_TELEMETRY` 권한만 부여한 전용 사용자(예: `thinglens-reader`)를 만들어 사용합니다. 대상 리소스: Device, Asset, Device/Asset Profile, Entity Group, Customer, Alarm.

### 3.2 수집 전략

- **계정**: 위 PE 읽기 전용 Generic Role 사용자 사용. 고객(Customer) 소유 범위로 제한된 사용자일 경우 분석 범위가 줄어듦을 UI에 명시.
- **수집 단계** (모두 §3.3 백그라운드 스케줄러가 수행)
  1. *메타데이터 동기화* (엔티티·프로파일·관계): 전체 1회 → 이후 증분
  2. *키 카탈로그 + 최신값*: 엔티티별 속성/텔레메트리 키 목록과 최신값 (`entitiesQuery/find`로 묶어서 조회)
  3. *샘플링 수집*: 키별 최근 N개(기본 500개) 원시값 → 데이터 타입·의미 추론용 (§5.0)
  4. *시계열 수집*: 분석 대상으로 지정된 키만, 워터마크 이후 구간만 증분 수집. 1분 해상도는 원시값(`agg=NONE`) 수집 후 로컬 집계, 장기 추세(1시간 이상 간격)는 서버 집계 (§3.6)
  5. *과거 백필(backfill)*: 가장 낮은 우선순위로, 야간 시간대에 작은 구간 단위로 천천히
- **버전 차이 흡수**: `ThingsBoardClient` 인터페이스 + 버전별 어댑터 (3.x / 4.x)

### 3.3 저부하 백그라운드 스케줄러

ThingsBoard 성능에 영향을 주지 않는 것을 **최우선 요구사항**으로 합니다.

**① 요청 예산 (Request Budget)**

| 설정 | 기본값 | 설명 |
|---|---|---|
| 전역 요청 속도 | 2 req/s (토큰 버킷) | 앱 전체에서 TB로 나가는 요청 상한 |
| 동시 요청 수 | 1~2 | 병렬 폭주 방지 |
| 페이지 크기 | 100 | 큰 페이지로 인한 TB DB 부하 방지 |
| 텔레메트리 요청 1건당 범위 | 최대 1일 × 키 5개, `limit` 지정 | 무거운 쿼리를 작게 분할 |
| 시간대별 예산 | 업무시간 20%, 야간(01–06시) 100% | 운영 피크 시간 회피 (크론 형태로 설정) |

**② 적응형 스로틀링 (AIMD + 서킷 브레이커)**

- 최근 요청의 응답 지연(p95)과 오류율을 지속 측정, 수집 시작 시 **기준 지연(baseline)** 기록
- p95 지연 > baseline × 2 또는 HTTP 429/5xx 발생 → 요청 속도 **절반으로 감소**, 정상 구간 지속 시 **조금씩 증가**
- 연속 오류 N회 → 서킷 오픈(예: 10분 정지) 후 1건 시험 요청으로 재개
- `Retry-After` 헤더 준수, 지수 백오프 + 지터(jitter)

**③ 작업 분할과 우선순위 큐**

- 모든 수집은 작은 **작업 단위(chunk)** 로 분할: (엔티티 × 키 묶음 × 시간 구간)
- 우선순위: 메타데이터 증분 > 키 카탈로그/최신값 > 의미 추론 샘플 > 분석 대상 시계열 증분 > 과거 백필
- 사용자가 분석을 요청했는데 캐시에 데이터가 없으면 → 즉시 TB를 호출하지 않고 해당 chunk의 **우선순위만 올림** (예상 완료 시간 표시)

**④ 증분·재개 가능성**

- 엔티티·키별 **워터마크**(마지막 수집 ts) 저장 → 이미 받은 구간은 재요청하지 않음
- 작업 상태를 DB에 체크포인트 → 앱 재시작 시 이어서 수행
- 메타데이터는 주기(기본 6시간)마다 증분 확인, 엔티티 수 변화 없으면 상세 조회 생략

**⑤ 요청 수 줄이기**

- `POST /api/entitiesQuery/find`로 다수 엔티티의 최신값을 한 번에 조회 (엔티티별 개별 호출 지양)
- 서버 측 집계(`agg=AVG`, 적절한 `interval`)로 원시 포인트 전송량 최소화
- 변경이 드문 데이터(프로파일, 관계)는 긴 주기로만 갱신

**⑥ 운영 가시성과 제어**

- 스케줄러 상태 화면: 현재 속도, TB 응답 지연 추이, 대기/완료 chunk 수, 예상 완료 시간
- **일시정지/재개 버튼**과 긴급 정지(kill switch), 설정 변경 즉시 반영
- 앱 자체 메트릭(Prometheus 형식): 분당 요청 수, 지연, 오류, 스로틀 상태

**구현**: 별도 `scheduler` 프로세스(APScheduler + SQLite 기반 작업 큐). API 서버와 분리하여 분석 부하가 수집 속도에 영향을 주지 않게 함. (규모가 커지면 arq + Redis로 교체 가능하도록 큐 인터페이스 분리)

### 3.4 500개 디바이스 기준 수집량·소요 시간 추정

가정: 디바이스 500 + 에셋 약 100, 디바이스당 텔레메트리 키 10개(총 약 5,000개 시계열), 기본 속도 2 req/s. 고빈도(1초) 키는 아래 §3.5에서 별도 산정

| 작업 | 예상 요청 수 | 2 req/s 기준 소요 |
|---|---|---|
| 엔티티·프로파일·그룹·고객 목록 (pageSize 100) | 약 30 | 수십 초 |
| 관계 (엔티티별 from 방향 조회) | 약 600 | 약 5분 |
| 속성 3개 스코프 | 약 1,800 | 약 15분 |
| 텔레메트리 키 목록 + 최신값 (`entitiesQuery` 묶음 조회) | 약 650 | 약 6분 |
| 의미 추론용 샘플 (키 5개씩 묶어 최근 500개) | 약 1,000 | 약 9분 |
| **초기 메타데이터 + 샘플 합계** | **약 4,000** | **약 35분** |
| 30일 시계열 백필 (1분 집계, 7일 단위 × 키 5개 묶음) | 약 4,500 | 약 40분 (야간 1회) |
| 일일 증분 (전체 키, 하루 1회) | 약 1,000 | 약 9분 |

→ 500개 규모에서는 **매우 보수적인 속도(초당 1~2건)로도 하룻밤 안에 전체 수집이 끝납니다.** 업무시간에는 0.5 req/s 이하로 낮춰도 증분 수집이 충분합니다.

### 3.5 고빈도(최소 1초) 보고 데이터 대응

1초 주기 키는 하루 86,400개 원시값이 쌓입니다. TB의 서버 측 집계(`agg=AVG`)도 **TB DB에서 원시값을 모두 읽어 계산**하므로,
"요청 수"가 적어도 요청 1건이 TB DB에 큰 부하가 될 수 있습니다. 따라서 요청 수뿐 아니라 **요청당 스캔량**도 제한합니다.

**① 보고 주기 측정 → 키별 수집 등급**

| 등급 | 보고 주기 | 수집 방식 |
|---|---|---|
| 고빈도 | < 10초 | 1개 키씩, 짧은 구간(기본 6시간) 원시값 수집 → 로컬 1분 집계, 야간 위주 |
| 중빈도 | 10초 ~ 5분 | 키 5개 묶음, 1일 단위 원시값 수집 → 로컬 집계 |
| 저빈도·이벤트형 | > 5분 또는 불규칙(변화 시 보고) | 키 5개 묶음, 7일 단위, 원시값(`agg=NONE`) 수집 |

**② 요청당 스캔량 상한**: `예상 원시값 수 = (구간 길이 / 보고 주기) × 키 수` 를 기본 **50,000건 이하**로 유지하도록 구간을 자동 분할 (설정 가능)

**③ 캐시 해상도 정책**
- 기본 캐시: **1분 집계(AVG·MIN·MAX)** — 상관·품질·변화 감지의 기본 입력
- 원시(1초) 데이터: **필요한 키·짧은 구간만** 온디맨드 고해상도 수집 (예: 원인 추적 시 사고 전후 1시간). 예산 범위 내에서 우선순위 큐로 처리
- 의미 추론용 샘플: 최근 500개만 가져오면 1초 키는 8분치뿐이라 편향 → **서로 다른 시간대 4개 구간에서 나눠 샘플링**

**④ 수집량 추정 (예: 전체 5,000개 키 중 10%인 500개가 1초 주기라고 가정)**

| 작업 | 예상 요청 수 | 2 req/s 기준 |
|---|---|---|
| 고빈도 키 30일 백필 (6시간 구간 × 1키) | 약 60,000 | 약 8.3시간 → **야간 2~3일에 나눠 수행** |
| 고빈도 키 일일 증분 | 약 2,000 | 약 17분 |
| 나머지 키 (§3.4 기준) | 약 5,500 | 약 45분 |

→ 고빈도 키의 초기 백필 기간은 **기본 7일**로 줄이고(약 2시간), 30일은 선택 사항으로 둡니다.
실제 1초 주기 키 수는 Phase 0 사전 진단으로 확정합니다.

### 3.6 Cassandra 저장소 고려사항

TB 시계열이 **별도 Cassandra 서버(16코어)** 에 저장되므로, 우리 앱의 읽기 요청은 `앱 → TB 노드 → Cassandra` 경로로 처리됩니다.
Cassandra는 동시에 1초 주기 데이터 **쓰기**도 처리하고 있어, 읽기 부하가 쓰기 지연으로 이어지지 않게 해야 합니다.

**① 서버 집계 vs 원시값 수집**

| 방식 | Cassandra에서 일어나는 일 | 적합한 경우 |
|---|---|---|
| 서버 집계 (`agg=AVG`, `interval=1분`) | TB가 요청 구간을 집계 간격 수만큼 나눠 **간격마다 Cassandra 조회** (예: 6시간 ÷ 1분 = 360회) → 조회 횟수 폭증 | 긴 기간·큰 간격 (예: 1년을 1일 간격 → 365회) |
| 원시값 수집 (`agg=NONE`, `limit`) | 파티션(기본 월 단위) 안에서 시간순 **연속 읽기** 1~수회 → Cassandra에 효율적 | 1분 해상도 데이터 확보 (기본 방식) |

- 기본: **원시값을 받아 앱에서 1분 집계(AVG·MIN·MAX·COUNT)** 후 저장
- 대신 TB 노드의 JSON 응답 생성·네트워크 전송량이 늘어나므로 요청당 최대 건수(§3.5 ②)로 제한
- 위 동작은 TB 버전·설정에 따라 다를 수 있어 **Phase 0에서 두 방식을 실측**하여 최종 확정 (측정 지표: TB API 응답 시간, TB 노드 CPU, 가능하면 Cassandra 읽기 지연)

**② 부하 감시 지표**
- 기본: 우리 요청의 TB API 응답 지연(§3.3 적응형 스로틀링 입력)
- 가능하면 추가: Cassandra 읽기/쓰기 지연(nodetool·JMX), TB 노드 CPU → 스로틀링 판단에 반영 (접근 권한 필요, §10)

**③ (선택) Cassandra 직접 읽기 모드 — Phase 0 검토 후 결정**
- TB 노드를 거치지 않고 앱이 Cassandra를 직접 **읽기 전용**으로 조회 (`ts_kv_cf` 등 TB 내부 테이블)
- 장점: TB 노드 부하 0, 파티션 단위 연속 읽기로 가장 효율적
- 단점: TB 내부 스키마에 의존(버전 업그레이드 시 깨질 수 있음), Cassandra 접속 권한·방화벽 필요, Cassandra 자체 부하는 그대로
- 기본은 REST 방식 유지, **REST 방식의 부하가 허용 기준을 넘을 때만** 채택

### 3.7 무기한 보존 대응 · 로컬 캐시 보존 정책 · 앱 서버 사양

TB에 데이터가 계속 쌓이므로 **"얼마나 과거까지 가져올지"** 와 **"우리 캐시에 얼마나 둘지"** 를 정합니다.

| 데이터 | 초기 백필 범위(기본) | 로컬 보존 |
|---|---|---|
| 1분 집계 | 중·저빈도 30일, 고빈도 7일 | 13개월 (계절성·전년 비교용) |
| 1시간 집계 | 최대 1년 (서버 집계, 야간 저속) | 무기한 (상관 기준선·장기 추세) |
| 원시값(1초 등) | 수집 안 함 (온디맨드만) | 7일 후 삭제 |
| 메타데이터 스냅샷 | — | 무기한 (diff만 저장) |

- 더 먼 과거가 필요하면 분석 화면에서 **기간 확장 요청** → 야간 예산 안에서 천천히 수집
- 용량 추정(상한): 키 5,000개 전부 1분 이하 주기라고 가정 시 1분 집계 1년치 약 30GB (Parquet 압축) + 원시 7일분 + 기타

**앱 서버 권장 사양 (별도 서버)**: 8코어 · 32GB RAM · SSD 1TB (최소 4코어 · 16GB · SSD 500GB)

## 5. 분석 기능 상세

### 5.0 텔레메트리·속성 데이터 종류 및 의미 추론

ThingsBoard는 키 이름과 값(`BOOLEAN/LONG/DOUBLE/STRING/JSON`)만 저장하고 **단위·의미 정보가 없습니다**.
따라서 `t1`, `temp`, `Temperature_C`가 같은 의미인지 앱이 추론해야 의미 있는 상관 분석이 가능합니다.
추론은 백그라운드에서 수집된 **샘플(키당 최근 N개)** 만으로 수행하여 TB 부하를 최소화합니다.

#### (1) 데이터 종류(타입) 추론

| 추론 타입 | 판별 근거 |
|---|---|
| 연속 수치 (continuous) | 실수, 고유값 많음, 분포 연속 |
| 누적 카운터 (counter) | 단조 증가 + 간헐적 리셋 (예: 누적 전력량 kWh, 가동 시간) → 분석 시 **차분값** 사용 |
| 이진/상태 (binary) | 고유값 2개 (`true/false`, `0/1`, `ON/OFF`) |
| 범주형 (categorical/enum) | 고유값 소수(≤ 20) 반복 문자열·정수 (예: `mode=AUTO/MANUAL`) |
| 타임스탬프 | epoch ms/s 범위의 정수, ISO 날짜 문자열 |
| 좌표 | 위도(−90~90)·경도(−180~180) 쌍, 키 이름 `lat/lng/lon` |
| 식별자/텍스트 | 고유값 비율 ≈ 1, 반복 없음 (시리얼 번호, MAC, 펌웨어 버전) |
| JSON 객체 | 하위 필드를 평탄화(`obj.field`)하여 각각 재추론 |
| 숫자 문자열 | `"23.5"` 같은 문자열 → 수치로 캐스팅 가능 여부 판단 |

**함께 계산하는 통계 프로파일**: 최소/최대/평균/표준편차, 고유값 수, 결측률, 소수점 자릿수,
**보고 주기**(타임스탬프 간격 중앙값), 변화 빈도, 단조성, 일주기 존재 여부.

#### (2) 의미(semantic) 추론 — 다중 근거 점수화

| 근거 | 예시 | 비중 |
|---|---|---|
| 키 이름 사전 매칭 | `temp, tmp, temperature, 온도` → temperature / `hum, rh` → humidity / `kwh` → energy / `rssi` → signal | 높음 |
| 단위 접미사 | `_c, _degC` → °C, `_v` → V, `_a` → A, `_pct` → % | 높음 |
| 값 범위 적합도 | 온도 −40~125, 습도 0~100, 배터리 0~100% 또는 2.5~4.2V, RSSI −120~0 dBm | 중간 |
| 동작 특성 | 누적 카운터 → energy/volume/runtime, 이진 → 상태/알람 | 중간 |
| 컨텍스트 | 디바이스 프로파일명(`TempSensor`), 같은 키를 가진 다른 디바이스들의 확정 의미 | 중간 |
| 분포 군집 | 이름이 달라도 분포·보고주기가 비슷한 키를 군집 → 같은 의미 후보 | 낮음 |
| LLM 추론 (선택) | 아래 (2-1) 참고 — 활성화된 경우에만 사용 | 활성 시 높음 |

- 결과: `의미 태그 + 단위 + 신뢰도(0~1) + 근거 목록`

#### (2-1) LLM 기반 의미 추론 (Claude API) — 선택 기능

> 현재 API 키가 없어 **기본 꺼짐**입니다. 꺼져 있으면 규칙·통계 근거만으로 추론하고, 확정 못한 키는 검토 대기 목록으로 보냅니다. 키를 설정하면 아래 기능이 켜집니다.

규칙·통계만으로는 `ch2`, `val_a`, `p1_out` 같은 불명확한 키나 한/영 혼용 키의 의미를 알기 어렵습니다. LLM을 정식 추론 단계로 사용합니다.

**입력 (키 1개 단위, 같은 디바이스 프로파일의 키를 묶어서 한 요청에 전달)**
- 키 이름, 출처(텔레메트리/속성 스코프), TB 값 타입, 추론된 데이터 종류
- 통계 요약(최소·최대·평균·고유값 수·보고주기·단조성), 대표 샘플값 최대 10개
- 컨텍스트: 디바이스 프로파일명, 부모 에셋 이름/프로파일, 같은 디바이스의 다른 키 이름 목록
- 규칙 기반 1차 추론 결과(있으면)

**출력 (구조화 출력 JSON 스키마로 강제)**
```json
{ "key": "p1_out", "semantic": "pressure", "unit": "bar",
  "category": "measurement", "description_ko": "1번 펌프 토출 압력",
  "confidence": 0.78, "reasoning": "프로파일 PumpController, 값 범위 0~12, 같은 디바이스에 p1_in 존재" }
```

**설계 원칙**
- **비용·호출 최소화**: 추론 단위를 "엔티티별 키"가 아닌 **(프로파일, 키 이름) 조합**으로 묶음 → 500개 디바이스라도 고유 조합은 수백 개 수준. 결과는 `llm_inference_log`에 캐시, 키·통계가 크게 바뀔 때만 재추론
- **대량 초기 추론은 Message Batches API** 사용 (실시간성 불필요, 비용 50% 절감), 이후 신규 키만 개별 호출
- 사전·규칙 지침이 담긴 시스템 프롬프트는 고정하여 **프롬프트 캐싱** 적용
- **규칙 + 통계 + LLM 결과를 앙상블**: 서로 일치하면 신뢰도 상향, 불일치하면 검토 대기 목록으로
- LLM은 **제안만** 하고, 사용자가 확정한 결과만 사전에 학습 반영
- 응답의 `stop_reason` 확인(거절·길이 초과 처리), 스키마 검증 실패 시 재시도, API 장애 시 규칙 기반 결과로 대체
- **데이터 전송 범위**: 키 이름·통계 요약·소량 샘플값·엔티티/프로파일 이름만 전송. 자격증명·좌표 등 민감 속성은 전송 전 마스킹 (마스킹 대상 키는 설정 가능)

**LLM 추가 활용**
- 데이터 카탈로그의 키 설명(`description_ko`) 자동 생성
- 상관 분석 결과(상위 상관쌍, 형제 이탈 센서)를 사람이 읽는 **요약 리포트 문장**으로 정리
- 누락 관계 추천 시 근거 설명 생성

- 신뢰도가 낮은 항목은 **검토 대기 목록**으로 → 사용자가 확정/수정 → 사전(`semantic_dictionary`)에 학습되어 다음 추론에 반영

#### (3) 속성(Attribute) 특화 추론

| 항목 | 방법 |
|---|---|
| 스코프 의미 | `CLIENT_SCOPE` = 디바이스 보고 정보(펌웨어 등), `SHARED_SCOPE` = 디바이스로 내려가는 설정, `SERVER_SCOPE` = 관리 메타데이터 |
| 정적/동적 구분 | `lastUpdateTs` 변경 횟수로 정적 속성(설치 위치, 모델)과 동적 속성(상태, 마지막 접속) 구분 |
| 역할 분류 | 식별(identity) / 위치(location) / 설정(config) / 상태(status) / 버전(firmware) |
| 키 중복 탐지 | 같은 의미의 키가 엔티티마다 다른 이름으로 존재(`location` vs `loc` vs `site`) → 표준화 제안 |

#### (4) 추론 결과의 활용

- 상관 분석 화면에서 **"같은 의미의 키" 자동 그룹화** (예: 에셋 하위 모든 온도 키를 한 번에 선택)
- 단위 정규화 (°F → °C, mV → V) 후 비교
- 누적 카운터는 자동으로 차분, 범주·이진형은 상관 대신 공발생/분할표(Cramér's V) 분석으로 전환
- 속성 정합성 검사(§5.2)의 "상속 일치 대상 키" 자동 제안
- 데이터 카탈로그 화면: 전체 키의 타입·의미·단위·보고주기·보유 엔티티 수를 한눈에 조회

### 5.1 토폴로지 분석 (구조적 상관관계)

| 항목 | 방법 |
|---|---|
| 관계 그래프 구축 | `relation` 테이블 → networkx `MultiDiGraph` (관계 유형을 엣지 속성으로) |
| 계층 트리 | `Contains` 관계 기준 루트 에셋 → 리프 디바이스 트리 (관계 유형은 설정 가능) |
| [PE] 그룹·소유자 교차 분석 | 관계 트리 vs 엔티티 그룹 vs 고객 계층의 **불일치** 탐지 (예: 에셋 A 하위 디바이스인데 다른 고객 소유, 같은 에셋 하위인데 그룹이 제각각) |
| 이슈 탐지 | 고아 디바이스(에셋과 연결 없음), 다중 부모, 순환(cycle), 빈 에셋, 과도한 깊이 |
| 통계 | 프로파일별 개수, 에셋당 디바이스 수 분포, 관계 유형별 개수, 연결 요소(component) 수 |
| 영향 범위 | 특정 에셋 선택 시 하위 전체(`maxLevel` 무제한) 엔티티 집합 |

### 5.2 속성 정합성 분석 (메타데이터 상관관계)

| 항목 | 방법 |
|---|---|
| 상속 일치 검사 | 사용자가 지정한 키(예: `location`, `site`, `zone`)가 부모 에셋과 하위 디바이스에서 일치하는지 |
| 프로파일 필수 키 | 프로파일별 "보유율" 계산 → 보유율 높은데 누락된 엔티티를 이상으로 표시 |
| 좌표 거리 | `latitude/longitude` 속성이 있을 경우 부모 에셋과 하위 디바이스 간 거리 이상치 |
| 속성 유사도 | 엔티티 간 속성 벡터 Jaccard/코사인 유사도 → 유사 엔티티 군집 |
| 비활성 탐지 | `active`, `lastActivityTime` 기반 장기 미통신 디바이스 목록 |

### 5.3 텔레메트리 상관 분석 (행위적 상관관계)

**입력**: 대상 엔티티 집합(에셋 하위 / 직접 선택), 키 목록, 기간, 집계 간격·함수

**전처리 파이프라인**

1. 캐시된 1분 집계 데이터를 공통 시간 격자로 정렬. **보고 주기가 섞인 경우**: 격자 간격 = 선택된 키 중 가장 느린 주기 이상(또는 사용자 지정), 이벤트형·저빈도 키는 직전값 유지(LOCF), 고빈도 키는 평균
   - 빠른 현상(초 단위 지연)의 지연 상관이 필요하면 짧은 구간에 한해 **고해상도 모드**(원시 1초 데이터 온디맨드 수집, §3.5)
2. 결측 처리: 짧은 공백은 선형 보간, 결측률 임계치(기본 30%) 초과 시리즈 제외
3. 문자열/불리언 텔레메트리 변환 (가능 시 수치화, 불가 시 제외)
4. **가성 상관 방지**: 선택적 차분(differencing)·추세 제거·일주기(seasonal) 제거 옵션

**분석 항목**

| 분석 | 방법 | 출력 |
|---|---|---|
| 상관 행렬 | 피어슨 / 스피어먼 / 켄달 | 히트맵 + 계층적 군집 정렬 |
| 유의성 | p-value + Benjamini–Hochberg FDR 보정 | 유의한 쌍만 강조 |
| 지연 상관 | 교차상관(CCF), 최대 상관 lag 탐색 | 쌍별 최적 lag 및 상관값 |
| 형제 이탈 탐지 | 같은 부모 에셋의 동일 키 시리즈 대비 개별 센서 상관 저하 | "그룹과 따로 노는 센서" 목록 |
| 에셋 집계 상관 | 에셋 단위 집계(평균/합) 시리즈 간 상관 | 에셋 간 상관 행렬 |
| 선행성 (선택) | Granger 인과성 검정 | 방향성 있는 영향 후보 (해석 주의 문구 포함) |

### 5.4 알람 공발생 분석

- 알람을 시간 구간(bin)으로 이산화 → 엔티티 쌍별 동시 발생 횟수, Jaccard 지수, Lift
- 관계 그래프 상의 거리와 공발생 강도를 함께 표시 → "구조상 멀지만 함께 울리는" 쌍 발견

### 5.5 누락 관계 추천

- 점수 = w1·(텔레메트리 상관) + w2·(속성 유사도) + w3·(알람 공발생) + w4·(이름 패턴 유사도)
- 현재 관계가 없는 디바이스–에셋 쌍 중 점수 상위 후보를 **추천 목록으로만** 제공 (TB에 자동 반영하지 않음)
- 사용자 피드백(채택/거절) 저장 → 가중치 조정 근거로 활용

### 5.6 LLM 꺼짐 / 켜짐 모드 비교

LLM은 선택 기능이며 **꺼진 상태에서도 모든 핵심 분석이 동작**해야 합니다.

| 기능 | LLM 꺼짐 (기본) | LLM 켜짐 |
|---|---|---|
| 키 의미 추론 | 규칙·통계·분포 군집만 사용, 불명확 키는 검토 대기 | LLM 추론 추가 → 불명확 키 자동 추론, 검토량 감소 |
| [A] 360° 요약 | 템플릿 문장 ("형제 대비 상관 저하: r 0.92→0.31") | 자연스러운 한글 요약 |
| [E] 원인 추적 설명 | 근거 목록(선행 시리즈·관계 거리·공발생) | 근거를 묶은 설명문 |
| [H] 정기 리포트 | 표·수치 중심 템플릿 리포트 | 요약문 추가 |
| [J] 자연어 질의 | **사용 불가** (메뉴 숨김) | 사용 가능 |
| 키 설명 자동 생성 | 수동 입력 | 자동 생성 |

| [D] 사용자·권한 | 사용자·역할·고객 범위 관리, 감사 로그 |

## 7. 개발 일정 (1인 기준 약 30.5주 / 2인 병렬 시 약 21.5주 예상)

LLM을 현재 사용하지 않으므로 **v1.0은 LLM 없이 완결**하고(27.5주차), LLM 기능은 키 확보 후 v1.1로 통합합니다(30.5주차).

|---|---|---|---|
| **Phase 0. 준비 + 사전 진단** | 1.5주 | ① **사전 진단 스크립트**(운영 TB 대상, 읽기 전용, 약 10분): TB 버전, 디바이스·에셋·키 수, 키별 보고 주기 분포(키당 최근 20개 원시값) ② 테스트용 **TB PE + Cassandra**(Docker) + 시드 데이터(이름 변형 키·누락 관계·고장 센서·1초 주기 키) ③ **Cassandra 수집 방식 실측**(서버 집계 vs 원시값) | 진단 리포트로 1초 키 수·버전 확정, 수집 방식 결정, §10 회신 |

## 10. 확인 필요 사항 (Phase 0에서 확정)

> ✅ 확정: PE 에디션, 디바이스 약 500개, 사내 설치, 보고 주기 디바이스별 상이(최소 1초), Cassandra 별도 서버(16코어), 앱 별도 서버, 데이터 무기한 보존, LLM 현재 미사용 (§0)
> 🔍 사전 진단으로 자동 확인: TB 버전, 1초 주기 키 수, 키·에셋 규모

1. **Cassandra 구성**: 노드 수(단일/클러스터), 복제 계수, TB 노드 서버 사양
2. **부하 모니터링 접근**: Cassandra(nodetool/JMX) 또는 TB 노드 CPU 지표를 앱에서 읽을 수 있는지 (없으면 API 응답 지연만으로 스로틀링)
3. **앱 서버**: 사양(권장 8코어·32GB·SSD 1TB), 인터넷 접근 가능 여부(오프라인 설치 필요 여부)
4. **접근 권한**: PE 읽기 전용 Generic Role 사용자 생성 가능 여부, 사전 진단 스크립트를 운영 TB에 실행해도 되는지
5. **허용 부하 기준**: 운영 피크 시간대, TB 테넌트 Rate Limit 설정값
6. **관계·명명 관례**: 계층 표현 관계 유형(`Contains` 외), 키 명명 규칙·단위 표기, 한/영 혼용
7. **알림 채널**: 사내 메일 서버(SMTP) 또는 Teams/Slack 웹훅 사용 가능 여부
8. **LLM 향후 계획**: 도입 예정 시점 (없으면 Phase 8 보류)

## 13. 목적 기반 추가 기능 (전체 채택 확정)

솔루션의 목적은 **"디바이스·에셋 간 관계를 이해하고 → 문제를 찾고 → 조치로 이어지게 하는 것"** 입니다.
현재 계획(§5)은 '이해'와 '발견'에 집중되어 있어, **지속 감시 · 원인 추적 · 조치 연결** 기능을 보강할 것을 제안합니다.
(A~L 12종 모두 채택, §7 일정의 각 Phase에 통합)

### 13.1 우선순위 요약

### 13.2 기능 상세

**A. 엔티티 360° 뷰**
- 디바이스/에셋 하나에 대해: 관계(상·하위), [PE] 그룹·소유자, 키 목록(의미·단위·품질), 최신값, 최근 알람
- **"가장 상관 높은 엔티티 Top 10"**, 형제 대비 이탈 여부, 관련 이슈 목록, TB 원본 페이지 링크
- LLM이 생성한 한 줄 요약: "3층 공조기 하위 온도 센서. 형제 센서 대비 최근 7일 상관 저하"

**B. 데이터 품질 점검·점수**
- 점검 항목: 장기 미보고(stale), **값 고정(flatline)**, 물리 범위 이탈(의미 추론 결과 활용), 결측·보고 주기 불규칙, 미래/역전 타임스탬프, 급격한 스파이크, 단위 불일치
- 디바이스·에셋·키 단위 **품질 점수(0~100)** → 상관 분석 시 품질 미달 시리즈 자동 제외 또는 경고
- 샘플·증분 데이터로 계산하므로 TB 추가 부하 없음

**C. 상관관계 변화 감지**
- 확정된 쌍(예: 같은 공간의 온도 센서끼리)의 **기준선 상관**을 학습 → 이동 구간(rolling window) 상관을 매일 계산
- 기준선 대비 유의미한 하락/상승 시 이벤트 생성 (예: r 0.92 → 0.31)
- 해석 예: 한 센서만 그룹과 어긋남 → 센서 고장/위치 변경 / 그룹 전체 변화 → 공정·환경 변화
- 일일 증분 수집 데이터만 사용 (TB 추가 요청 없음)

**D. 고객(소유자) 범위 기반 접근 제어**
- 앱 사용자에 TB 고객(Customer) 범위를 매핑 → 해당 고객 소유 엔티티만 조회·분석 가능
- 관리자: 전체 / 고객 담당자: 자기 고객 범위만. 접근·내보내기 감사 로그

**E. 원인·영향 추적 (RCA)**
- 알람·이상 이벤트 선택 시: 관계 그래프 상 인접 엔티티 + 지연 상관상 **선행(먼저 변한) 시리즈** 순위 제시
- 반대로 "이 디바이스가 멈추면 영향받는 하위/연관 엔티티" 영향 범위 표시
- LLM이 근거를 묶어 원인 후보 설명 생성 (확정 판단이 아닌 후보 제시임을 명시)

**F. 센서 중복·측정 공백 분석**
- 중복: 같은 의미·같은 에셋에서 상관 ≥ 0.98 → 중복 센서 후보 (예비용인지 확인 필요)
- 공백: 형제 에셋은 모두 가진 의미(예: 습도)를 특정 에셋만 없는 경우 → 측정 공백 후보

**G. 조치용 내보내기**
- 누락 관계 추천·속성 불일치·키 이름 표준화 결과를 **TB 일괄 가져오기(CSV) 형식** 또는 REST 호출 스크립트로 내보내기
- 앱은 TB에 쓰지 않음(읽기 전용 원칙 유지) — 사람이 검토 후 TB에서 적용

**H. 정기 건전성 리포트 + 알림**
- 주간/일간: 신규 이슈, 품질 점수 변화, 깨진 상관, 신규 키·디바이스 → LLM이 한글 요약문 작성
- 이메일·웹훅(Slack/Teams) 발송, 심각도 기준 설정

**I. 메타데이터 스냅샷·변경 이력**
- 동기화마다 관계·그룹·키 목록·주요 속성의 차이(diff) 저장 → 변경 타임라인
- C·E와 결합: "상관이 깨진 시점 직전에 관계/설정이 바뀌었는가?"

**J. 자연어 질의** — "2공장에서 형제와 따로 노는 온도 센서 보여줘" → 분석 조건으로 변환 후 실행 (LLM은 조건 생성만, 계산은 분석 엔진)

**K. 분석용 데이터셋 내보내기** — 에셋 단위로 시간 정렬된 Parquet/CSV, Jupyter 예제 노트북 제공

**L. 표준 키 명명·프로파일 템플릿 제안** — 같은 의미의 키 이름 변형(`temp`/`Temperature`/`t1`)을 모아 표준 이름·단위 제안
