# Phase 0 실측: Cassandra 환경에서 서버 집계 vs 원시값 수집

- 측정일: 2026-11-16
- 환경: ThingsBoard CE **4.3.1** + PostgreSQL 16(엔티티) + **Cassandra 4.1**(시계열), 단일 노드 (`deploy/test-env`)
- 데이터: `tools/seed_thingsboard.py` 시드 (1초 주기 펌프 키, 1분 주기 온도 키 등)
- 도구: `tools/bench_agg_vs_raw.py` — 방식별 5회 반복, Cassandra 읽기 수는 `nodetool tablestats thingsboard.ts_kv_cf` 의 Local read count 증가량
- 같은 측정을 두 번(직접 실행한 TB, docker compose TB) 수행해 같은 결과 확인

## 결과 1 — 1초 주기 키, 6시간 구간 (원시값 약 21,600개)

| 방식 | 응답 중앙값 | 반환 점 수 | 응답 크기 | **Cassandra 읽기/요청** |
|---|---|---|---|---|
| 서버 집계 1분 (AVG, 360구간) | 271~305 ms | 359 | 17 KB | **360** |
| 서버 집계 1시간 (AVG, 6구간) | 193~197 ms | 6 | <1 KB | 12 |
| 원시값 (agg=NONE, limit 50,000) | 173~205 ms | 21,514 | 874 KB | **11** |

## 결과 2 — 1분 주기 키, 7일 구간 (원시값 약 10,080개)

| 방식 | 응답 중앙값 | 반환 점 수 | 응답 크기 | **Cassandra 읽기/요청** |
|---|---|---|---|---|
| 서버 집계 1분 (10,080구간) | — | — | — | **TB가 거부 (HTTP 400)** |
| 서버 집계 1시간 (AVG, 168구간) | 189 ms | 168 | 8 KB | **168** |
| 원시값 (agg=NONE, limit 50,000) | 198 ms | 10,077 | 412 KB | **6** |

## 확인된 사실

1. **TB 서버 집계는 "집계 구간 1개 = Cassandra 조회 1회"** 로 동작한다. 1분 집계 6시간 = 360회.
   TB 설정 주석도 이를 명시: `ts_max_intervals: 700 # Max number of DB queries generated by a single API call`
2. **요청 1건의 집계 구간이 700개를 넘으면 TB가 거부**한다 (`DATABASE_TS_MAX_INTERVALS`, 기본 700).
   → 1분 집계는 최대 약 11.6시간, 1시간 집계는 최대 약 29일 구간까지만 한 번에 요청 가능
3. **원시값 수집은 Cassandra 읽기가 30~60배 적다** (파티션 내 연속 읽기를 페이지 단위로 수행).
   대신 응답 크기가 크다 (6시간·1초 키 기준 약 0.9MB). 응답 시간은 비슷.

## 결정 (계획서 §3.6·§3.7 반영)

| 항목 | 결정 |
|---|---|
| 기본 수집 방식 | **원시값(agg=NONE) 수집 → 앱에서 1분·1시간 집계** (확정) |
| 서버 집계 | 사용하지 않음. 예외적으로 쓸 때도 요청당 구간 ≤ 100으로 제한 |
| 장기 이력(30일 초과) | 원시값을 야간에 천천히 수집해 로컬에서 1시간 집계 생성. 고빈도 키는 기본 7일, 그 이상은 요청 시에만 |
| 요청당 원시값 상한 | 50,000개 유지 (응답 약 2MB 이하) |

## 운영 환경에서 다시 확인할 점

- 운영 Cassandra(별도 서버, 16코어)는 실제 데이터가 많아 파티션이 크고, 1초 쓰기가 동시에 일어남 → **운영(또는 스테이징)에서 짧은 구간으로 1회 재측정** 권장
  ```bash
  python3 tools/bench_agg_vs_raw.py --url https://tb.사내 --username reader --device <1초 디바이스명> --key <키> --hours 1 \
      --nodetool "ssh cassandra-server nodetool"   # nodetool 접근이 없으면 생략 (응답 시간만 비교)
  ```
- 운영 TB의 `DATABASE_TS_MAX_INTERVALS` 값 (기본 700에서 바뀌었는지)

## 추가 실측 (Phase 2) — 구간 1개짜리 집계 (MIN·MAX·COUNT)

드물게 생기는 이상값(예: 7일 중 15번뿐인 습도 130%)은 샘플 수십 개로는 잡히지 않는다.
집계 구간을 **1개**(interval = 전체 구간)로 하면 구간 수만큼 조회가 쪼개지는 문제가 없는지 측정했다.

| 대상 | 구간 | Cassandra 읽기 | 응답 | 결과 |
|---|---|---|---|---|
| 1분 키 (습도), MAX | 7일 1구간 | 6 | 168 ms | 130.0 (스파이크 검출) |
| 1분 키 (습도), MIN | 7일 1구간 | 6 | 112 ms | 19.4 |
| 1초 키 (전류), MAX | 7일 1구간 (실제 데이터 6시간) | 22 | 277 ms | 23.0 |

결정: **구간 1개짜리 MIN·MAX·COUNT 집계 허용** (`TbAdapter.ts_agg` 가 interval = 전체 구간을 강제).
단 1초 키 7일은 60만 행을 TB가 읽어야 하므로, 범위 창을 **키당 원시값 약 1만 개 이내**로 제한한다
(1초 키 ≈ 2.8시간, 1분 키 ≈ 7일). 테스트용 가짜 TB도 구간이 여러 개인 집계 요청을 거부하도록 해 규칙을 강제한다.
